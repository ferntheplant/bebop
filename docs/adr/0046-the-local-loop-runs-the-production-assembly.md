# The local loop runs the production assembly

The end-to-end loop on a developer's laptop runs bebop's API and worker, the Swordfish daemon, and Postgres — the same packed artifacts production runs, over loopback, against a Postgres container the operator starts from `compose.yml`. This is a permanent mode used to develop bebop itself, not scaffolding with a death date, and it is a configuration of the production system rather than a second assembly: local and production differ only in which layer an entrypoint provides, never in a conditional inside a service.

Swordfish is treated as though it ran in an insecure environment even though locally it does not. No Swordfish code reaches bebop's state except through the wire protocol — evidence upload included, and bebop's Postgres never. Both processes run as the same user on the same disk, so the seam protects nothing here and cannot be enforced by anything local; it is a review rule. Local testing is end-to-end smoke of the whole system without VMs or external networks, and it will not catch a violation. An agent that goes looking through the database or the credential material to cheat is a failure mode this mode is not built to detect.

Two alternatives were weighed and rejected. **Swordfish alone**, taking GitHub and evidence directly, is one daemon and one SQLite file with no Postgres — but pull-request creation and evidence ingestion do not exist yet, so the cost is not moving code across the seam later, it is writing new code on the wrong side of [Bebop owns authority, Swordfish owns the loop (ADR 0002)](./0002-bebop-owns-authority-swordfish-owns-the-loop.md) from the start, which is what [`ABSTRACT.md`](../../ABSTRACT.md) §3.10 warns encodes itself into every caller. It also unpicks a shipped path: Swordfish's `bebopWebSocketUrl` and `bebopToken` are mandatory, and the operator credential gating every mutating `sf` command is derived by bebop and retrieved through an authenticated bebop client. **Bebop reduced** — the authority for GitHub and evidence, but on SQLite without the worker — foundered on the schema. Bebop's persistence is Postgres-specific in kind rather than in dialect: `jsonb` columns with explicit casts and a separate fingerprint column because `jsonb` reorders keys, `timestamptz` throughout, `pg_advisory_xact_lock` serializing migration-table creation, and job claiming through `FOR UPDATE SKIP LOCKED`. Dropping Postgres locally buys a second persistence implementation, which is the divergence this ADR exists to prevent.

## Consequences

The operator starts Postgres and both bebop processes by hand. The Swordfish daemon is not one of them: the lifecycle provider is what makes a daemon exist in both environments, so locally the fake provider starts the process, exactly as exe.dev's provider will have the VM's bootstrap start it. This is not bebop taking process authority over Swordfish — bebop core calls `provision` and learns nothing about how a machine comes to be running, which is the same interface in both environments and the reason the divergence stays inside the one implementation exe.dev replaces. The machine credential therefore never leaves the path [Swordfish tokens are bounty-scoped (ADR 0014)](./0014-bounty-scoped-swordfish-tokens-minted-at-provisioning.md) defines, because it goes from derivation straight into the process the provider starts. Bebop being unreachable is a normal state rather than an error — Swordfish keeps working under [Bebop owns authority, Swordfish owns the loop (ADR 0002)](./0002-bebop-owns-authority-swordfish-owns-the-loop.md) and may reach ready with nobody listening — so it reconnects with backoff and reports connection state in `sf status` beside the stage. It is not `needs_attention`: no decision is waiting, only a process.

The bounty's working copy is a fresh clone in a bounty-scoped root, never the operator's own checkout. [Verification runs in a clean-room worktree (ADR 0015)](./0015-verification-runs-in-a-clean-room-worktree.md) and the clean-tree precondition on candidate submission are both unverifiable against a directory holding uncommitted work.

Two GitHub identities exist locally, from two sources, as in production. Bebop uses a real GitHub App installation for pull-request creation, check polling, and the ruleset verification [The merge target must enforce rulesets (ADR 0034)](./0034-the-merge-target-must-enforce-rulesets.md) requires — that identity is bebop's in both environments, so building it any other way would put an untested credential-acquisition path into production. The machine uses the operator's ambient Git and `gh` credentials, which is structurally what exe.dev's repository-scoped integration provides: ambient to the machine, never handled by bebop or Swordfish. The fake provider therefore injects nothing for GitHub, and attaching the real integration later changes no bebop or Swordfish code.

Two local compromises are accepted rather than hidden. The ambient credential is not repository-scoped where exe.dev's is, which costs nothing the local destination claims — `ABSTRACT.md` §8 criterion 3 is out of its scope. And `BEBOP_LOCAL_HARNESS_ROOT` writes a plaintext machine credential to disk, which already warns at startup rather than passing silently.
